# Milestone 2: ActivityPub Server-to-Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the `quarkus-activitypub` repo (`activitystreams-model`, `quarkus-nodeinfo`, `quarkus-activitypub`, `quarkus-activitypub-hibernate`, `quarkus-activitypub-test`, BOM) so a Quarkus app can expose actors, accept follows and deliver signed activities, after two small Tier 1 changes.

**Architecture:** One new multi-module git repo `OpenWebExt/quarkus-activitypub/`. A plain Jackson model library; a NodeInfo extension; the server-to-server extension built on the three Tier 1 extensions (safe-fetch for every outbound call, webfinger resolver for discovery, http-signatures for inbox verification and delivery signing); a Hibernate ORM module replacing the in-memory store defaults; a test module with a fake remote instance.

**Tech Stack:** Java 21, Maven, Quarkus 3.40.1, Vert.x routes, Jackson, Mutiny, Caffeine, Quarkus Scheduler, Hibernate ORM + H2 (tests), JUnit 5 + `QuarkusUnitTest`, REST Assured.

**Spec:** `docs/superpowers/specs/2026-10-25-milestone-2-activitypub-s2s-design.md` (the design) and `Quarkus Open Web Extensions — Architecture Spec.md` (conventions, Tier 2 outline).

## Global Constraints

- Java 21; Quarkus `3.40.1`; Apache 2.0; groupId `org.sitenetsoft.quarkus`; version `0.1.0-SNAPSHOT` everywhere.
- Packages: `org.sitenetsoft.activitystreams` (model, no Quarkus dependency), `org.sitenetsoft.quarkus.nodeinfo`, `org.sitenetsoft.quarkus.activitypub`, `org.sitenetsoft.quarkus.activitypub.hibernate`.
- Config prefixes `quarkus.nodeinfo.*`, `quarkus.activitypub.*`; logging categories `org.sitenetsoft.quarkus.nodeinfo`, `org.sitenetsoft.quarkus.activitypub`.
- Every extension module: `quarkus-extension-processor` annotation processor, runtime `quarkus-extension-maven-plugin` (`extension-descriptor`), `META-INF/quarkus-extension.yaml` (status `experimental`), `quarkus-skill.md`.
- `@ConfigMapping` roots, build-time and runtime in separate interfaces, defaults only via `@WithDefault`.
- Server endpoints are Vert.x `RouteBuildItem` routes at the server root (absolute routes via `HttpRootPathBuildItem.routeBuilder().route("/…")`), warning when `quarkus.http.root-path` is not `/`. Same pattern as `WebFingerProcessor` + `BeanHandler`.
- Blocking `Foo` and Mutiny `ReactiveFoo` for every client/SPI, one implementation. SPI defaults are `@DefaultBean`; multi-implementations are injected with `@All List<T>`. SPI types are `UnremovableBeanBuildItem.beanTypes(...)`.
- Secure defaults: all outbound HTTP through `SafeFetchClient`/`ReactiveSafeFetchClient`; never log private keys, signature values or bearer tokens.
- Host rules: `JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64`, Maven `-T 8` max, one build at a time, Surefire `<argLine>-XX:TieredStopAtLevel=1</argLine>`; no `native-image` locally. Commit before every build.
- Tier 1 artifacts come from the local Maven repo at `0.1.0-SNAPSHOT`; rebuild order after a Tier 1 change: safe-fetch → webfinger → http-signatures → activitypub.
- Parent POM content: copy `quarkus-webfinger/pom.xml` (BOM import, compiler plugin with the extension processor, surefire argLine and `java.util.logging.manager`), add modules.
- Content type constant: `application/activity+json`; accepted on input also `application/ld+json; profile="https://www.w3.org/ns/activitystreams"` and `application/ld+json`.

## Review Focus

1. **Inbound activity whose `id` is missing** (Mastodon sends `Undo` and `Delete` without ids at times): must be processed, not rejected; dedup is skipped for id-less activities. Test in Task 10.
2. **Inbox body that is valid JSON but not an object** (array, string): must answer `400`, never `500`. Test in Task 10.
3. **Follower whose inbox cannot be resolved** at delivery time (actor fetch fails): the other deliveries of the same activity still go out; the failed one is `FAILED` with the error recorded. Test in Task 11.
4. **Actor document whose `publicKey` is an array** (some servers) or whose `id` has a trailing slash difference from the key id's host casing: the key resolver must accept the array form and compare hosts case-insensitively. Test in Task 9.
5. **Username with characters that need percent-encoding in the path template** or that differs only in case from a stored actor: actor lookup is exact-match, URLs encode the username, and WebFinger normalises `acct:` user part through `AcctUri`. Test in Task 8.
